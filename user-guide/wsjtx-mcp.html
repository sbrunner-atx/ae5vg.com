At a glance

WSJT-X does not offer a request-and-response API. It broadcasts state over UDP (Status, Decode, QSOLogged, Heartbeat) and honors a small set of inbound control messages. wsjtx-mcp runs a background UDP listener that continuously parses datagrams and keeps the latest status, a buffer of decodes and the completed QSOs; you read those, and nudge WSJT-X with control messages.

Four consequences worth knowing up front:

  • No dial-frequency control over UDP. You can read the dial from Status and set mode, sub-mode, Rx DF and T/R period via configure, but QSY is a rig-control concern (Hamlib, CAT or the UI), not this server.
  • You can start and halt Tx, but cannot toggle Enable Tx. Transmission is started by answering a CQ (reply) or by free text with send, and stopped by halt. The Enable Tx, Auto Seq, Call 1st and Hold Tx Freq checkboxes stay UI settings.
  • reply gives hands-free QSOs only when Auto Seq is on. A reply is equivalent to double-clicking a CQ; with Auto Seq enabled (the usual FT8 and FT4 default) WSJT-X sequences the whole exchange to QSOLogged with no further calls. With Auto Seq off, reply starts only the first transmission.
  • Best for search and pounce, weak for RUN. The API is built to answer CQ and QRZ decodes, so search and pounce is fully automatable. It has no clean way to drive a repeating call-CQ cycle; that needs WSJT-X's own Enable Tx, or a free-text CQ re-sent each period.

The protocol is schema 3 / Qt_5_4, stable across WSJT-X 2.1 through 3.x, verified live against WSJT-X 3.0.2.

Installing

1 · Enable WSJT-X's UDP Server

In WSJT-X: Settings → Reporting → UDP Server. UDP Server: the host running wsjtx-mcp; for a local setup leave it at 127.0.0.1. Port: 2237, the default. Accept UDP requests: tick this if you want wsjtx-mcp to control WSJT-X (answer CQs, set free text, configure); it is off by default. Observing decodes and status works without it; commanding does not.

2a · As a Claude Desktop extension

  1. Download wsjtx-mcp.mcpb from Downloads.
  2. If you previously installed an older build, remove it first (Settings → Extensions → uninstall, and wait for its tile to disappear) so the swap takes effect.
  3. Double-click the .mcpb, or drag it onto Claude Desktop → Settings → Extensions.
  4. Fill in the settings form: your operator callsign (blank for receive-only; set it to enable transmit), and the listen host and port, usually 127.0.0.1 and 2237.
  5. Quit and reopen Claude Desktop (⌘Q) so the new tools load.
Enables transmit

Entering your callsign, together with Accept UDP requests in WSJT-X, lets wsjtx-mcp key the transmitter through reply and free_text with send=true. Leave the callsign blank until you have read the transmit gate chapter.

2b · From PyPI, any MCP client

uvx wsjtx-mcp        # or: pipx run wsjtx-mcp

Add it to your client's MCP config with the environment variables from the configuration table in How it works, for example:

{
  "mcpServers": {
    "wsjtx-mcp": {
      "command": "uvx",
      "args": ["wsjtx-mcp"],
      "env": { "WSJTX_CALLSIGN": "", "WSJTX_HOST": "127.0.0.1", "WSJTX_PORT": "2237" }
    }
  }
}

3 · Verify

Ask your client to run the status tool. You should see the current dial frequency, mode and the discovered instance within about 15 seconds (WSJT-X sends a Heartbeat every 15 s plus a Status on each state change). If nothing appears, run diagnostics; it reports whether the UDP listener bound and how many datagrams have arrived.

Your first session

What is WSJT-X doing right now? status: dial frequency, mode, DX call, transmit state, instance health Show me the last few decodes on this band. decodes read: the buffered Band Activity Answer the strongest CQ on this band. reply; with Auto Seq on, WSJT-X runs the whole exchange to QSOLogged Log that contact to N3FJP. the log tool returns the buffered QSO; the assistant passes it to n3fjp-mcp stop transmit halt; always allowed
Keys the transmitter

Answering a CQ puts the station on the air. With WSJTX_CALLSIGN blank the request is refused. You remain the control operator under Part 97: stay where you can intervene, and say "stop" to halt.

How it works

WSJT-X is mostly a broadcaster. It pushes Status, Decode, QSOLogged, LoggedADIF, WSPRDecode, Clear, Close and a Heartbeat every 15 seconds. There is no "get frequency" or "get mode" query; you learn state from Status.

The listener keeps three things current. The first is the latest Status snapshot. The second is a decode buffer you can read, drain, clear or replay. The third is the completed QSOs from QSOLogged and LoggedADIF messages, ready to feed the logger.

Control works only with Accept UDP requests on. Every control message must carry the target instance's Id, which the server learns by first receiving a datagram from it. Control replies go back to the address each datagram arrived from. Host and port in the settings are where this server listens.

Points to design around, from the message reference:

  • reply must exactly match a prior CQ or QRZ decode; it is equivalent to double-clicking that line.
  • configure sets mode, sub-mode, Rx DF, T/R period, frequency tolerance, DX call and grid, but not the dial frequency. On WSJT-X 3.0.x a mode change may move the dial to that band and mode's default frequency.
  • Only one process can bind a UDP port. This is a UDP and operating-system fact, not a WSJT-X limit.

The codec is pure standard library and covers all 17 message types. The wire-level details are in WSJTX-API (PDF).

The transmit gate

Can key a transmitter

The callsign is the single transmit gate. With WSJTX_CALLSIGN blank the server is receive-only: it refuses every transmit-initiating message, namely reply, free_text with send=true, and any keying message via wsjtx_call. Halt, clear, configure, highlight, location, replay and all reads are always available; they do not put you on the air, and halt takes you off. Per-transmit approval also comes from your client's tool-permission prompt, and WSJT-X's own Tx Watchdog and the Tx Enabled and Transmitting flags in status are extra safety signals. You, the licensed control operator, remain responsible for lawful operation: station identification, the ability to intervene, and the Part 97 automatic and remote-control rules.

Running alongside other UDP tools

Only one process can own UDP 2237 on a host. If JTAlert, GridTracker or N1MM already consume it, three options:

  1. Point WSJT-X's secondary UDP server at wsjtx-mcp's host and port.
  2. Use a multicast group: set the same group in WSJT-X's UDP Server and in WSJTX_MULTICAST, so several listeners coexist.
  3. Run wsjtx-mcp on a different host than WSJT-X, bridged by mcp-host-bridge (next section).

The remote host

Sandboxed MCP clients, notably Claude Desktop, let their connector reach only 127.0.0.1, not LAN addresses, even with macOS Local Network permission on. The fix is a small UDP relay that runs outside the sandbox on the wsjtx-mcp host: mcp-host-bridge, which routes WSJT-X's broadcasts in and your control replies back out. UDP is connectionless and bidirectional, so the topology inverts versus TCP: the bridge listens on the LAN and delivers to loopback.

Get the bridge with Python, or download the single binary for your OS from Downloads; the binary needs no Python.

uvx mcp-host-bridge --help          # or: pipx install mcp-host-bridge

Then install the persistent wsjtx bridge service on the wsjtx-mcp host. The same commands work on every OS: launchd on macOS, systemd on Linux, a Scheduled Task on Windows. netsh portproxy is TCP-only and is skipped for UDP automatically.

mcp-host-bridge install wsjtx --to <remote-wsjtx-host>
# listens 0.0.0.0:2237 (LAN) and delivers 127.0.0.1:2238 (loopback);
# --to is an optional hint; the remote peer is auto-learned from the first datagram
mcp-host-bridge status wsjtx       # check it
mcp-host-bridge uninstall wsjtx    # remove it

Critical wsjtx-mcp config for the bridged case: WSJTX_HOST=127.0.0.1 and WSJTX_PORT=2238, the bridge's deliver port, not the default 2237 (the bridge's own LAN socket occupies 2237 on that host). In the remote WSJT-X, set Settings → Reporting → UDP Server to the bridge host's LAN IP, port 2237, and tick Accept UDP requests for control.

Notes: for a local WSJT-X on the same machine you do not need the bridge at all; point wsjtx-mcp straight at 127.0.0.1:2237. Multicast is an alternative to the bridge when every consumer is on the same LAN segment: set WSJTX_MULTICAST and WSJT-X's UDP Server to the same group. Full details: REMOTE-HOST.md.
