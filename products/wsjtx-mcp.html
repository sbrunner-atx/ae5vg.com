wsjtx-mcp

An MCP server that controls WSJT-X, the weak-signal program for FT8, FT4, JT65, MSK144, Q65 and WSPR, from MCP clients such as Claude Desktop. It is the weak-signal leg of an operate-then-log trio: fldigi-mcp operates the broad digital modes, n3fjp-mcp logs, wsjtx-mcp operates the FT8 and FT4 world.

What it does

WSJT-X does not offer a request-and-response API. It broadcasts state over UDP (Status, Decode, QSOLogged, Heartbeat) and honors a small set of inbound control messages. This server runs a background UDP listener that continuously parses datagrams. It keeps the latest status, a buffer of decodes and the completed QSOs; you read those, and nudge WSJT-X with control messages.

Some consequences are worth knowing up front. There is no dial-frequency control over UDP. You can read the dial from Status and set mode, sub-mode, Rx DF and T/R period via configure, but QSY is a rig-control concern (Hamlib, CAT or the UI). You can start and halt Tx, but you cannot toggle Enable Tx. Transmission is started by answering a CQ (reply) or by free_text with send=true, and stopped by transmit halt. The Enable Tx, Auto Seq, Call 1st and Hold Tx Freq checkboxes stay UI settings.

That makes it best for search and pounce and weak for RUN. The API is built to answer CQ and QRZ decodes, so search and pounce is fully automatable. A repeating call-CQ cycle needs WSJT-X's own Enable Tx in the UI, or a free_text CQ re-sent each period.

The protocol is schema 3 / Qt_5_4, stable across WSJT-X 2.1 through 3.x, verified live against WSJT-X 3.0.2.

Experimental

wsjtx-mcp is experimental. Transmit is gated behind your callsign, and you remain the operator in command; read Safety before you set the callsign.

How it works

In WSJT-X, set Settings → Reporting → UDP Server to the host running this server, port 2237. Turn Accept UDP requests on to allow control; it is off by default. Observing decodes and status works without it.

Only one process can normally own UDP 2237 on a host. If JTAlert, GridTracker or N1MM already consume it, point WSJT-X's secondary UDP server here, use a multicast group so several listeners coexist, or run this server on a different host.

To reach a WSJT-X on another machine, install mcp-host-bridge on the computer that runs this server: mcp-host-bridge install wsjtx --to <rig-host>. Then set WSJTX_PORT=2238. Sandboxed MCP clients reach only loopback, and the bridge does the LAN hop.

Ask it

What is WSJT-X hearing on this band? the decodes tool reads the buffered Band Activity Answer the strongest CQ on this band. reply; with Auto Seq on, WSJT-X runs the whole exchange to QSOLogged Log that contact to N3FJP. the log tool returns the buffered QSO; the assistant passes it to n3fjp-mcp stop transmit halt; always allowed
Keys the transmitter

Answering a CQ puts the station on the air. With WSJTX_CALLSIGN blank the request is refused. You remain the control operator under Part 97: stay where you can intervene, and say "stop" to halt.

Safety

Can key a transmitter

The callsign is the single transmit gate, exactly as in fldigi-mcp. With WSJTX_CALLSIGN blank the server is receive-only. It refuses reply, free_text with send=true, and any keying message via wsjtx_call. Halt, clear, configure, highlight, location, replay and all reads are always available; they do not put you on the air, and halt takes you off. Per-transmit approval comes from the client's tool-permission prompt. WSJT-X's own Tx Watchdog and the Tx Enabled and Transmitting flags, surfaced in status, are extra safety signals. Operating under Part 97 automatic or remote control is the operator's responsibility: ensure station identification and a control operator who can intervene.
