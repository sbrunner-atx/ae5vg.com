n3fjp-mcp

An MCP server for logging amateur radio QSOs to N3FJP logging software, Amateur Contact Log and the 100-plus N3FJP contest loggers, from MCP-aware clients such as Claude Desktop. Every program in the suite shares one TCP control API; n3fjp-mcp speaks that protocol directly, so an assistant can log contacts, read the log, run dupe checks and manage band and mode through plain language.

What it does

It is the logging half of an operate-then-log workflow; its sibling fldigi-mcp operates the radio. The headline tool runs the real N3FJP flow, the same sequence a keyboard would produce: set the call, fire CALLTAB for the dupe check and previous-contact lookup, fill the exchange, send ENTER, and report the records added plus any dupe detail. Whether the QSO was logged is judged from the QSO-count change or an ENTEREVENT, because ENTERRESPONSE can report 0 on a QSO that was written.

It is written against the protocol with Python's standard-library socket, no third-party wrapper; the only runtime dependency is the MCP SDK. Verified live against N3FJP's ARRL Field Day Contest Log, API version 2.2. The protocol is shared across the suite, but field sets vary per contest; the fields tool confirms what the running program uses.

How it works

The verified TCP protocol

Checked live against N3FJP's ARRL Field Day Contest Log 6.6.10 reporting API version 2.2. Details from the N3FJP TCP API reference.

TopicWhat was verified
TransportPlain TCP. N3FJP is the server, the connector the client. Default port 1100. Each command ends with CR LF.
EnvelopeEvery command and response is wrapped as <CMD><COMMANDID><TAG>value</TAG></CMD>. One packet can carry several blocks, so the stream is read continuously and split on </CMD>, never on newlines.
StreamResponses and opt-in notifications share one socket; a background reader routes each block to the waiting request or to a notification buffer.
API port, not networking portPort 1100 is the API. Port 1000 is N3FJP's multi-PC networking socket; API commands sent there return nothing.
Unknown commandsAnswer <CMD><CMD_NOT_FOUND></CMD> rather than silence, so "not supported" can be told from "wrong port".
Changed since 0.9There is no APIVERSION command; read the APIVER tag from PROGRAM. READQSOCOUNT became QSOCOUNT; ALLFIELDSVALUES is gone because ALLFIELDS includes values; READUSERDATA is not present.
Logging flowUPDATE TXTENTRYCALL, ACTION CALLTAB, UPDATE the exchange boxes, correct band and mode, ACTION ENTER, read the response.
CALLTABEVENTOne block a beat after CALLTAB carries country, DXCC, both zones, prefix, continent, bearing, long path and distance; a CALLTABDUPEEVENT follows for a dupe.
ENTER can report 0 yet still logIn Network mode the master-table commit is asynchronous, so ENTERRESPONSE can return 0 for a QSO that was written. Success is checked by the QSOCOUNT change instead.

Where the connector runs

If N3FJP runs on the same computer as the client, leave the host at 127.0.0.1 and enable Settings → Application Program Interface → TCP API Enabled, port 1100, and you are done.

If N3FJP runs on a different computer, there is a catch: a sandboxed MCP client runs the connector so it can only reach loopback, so putting N3FJP's LAN IP in the settings will time out even though telnet to that IP works. mcp-host-bridge on the client computer fixes it; the diagnostics tool helps confirm whether you need it. Keep the link on a trusted LAN, the API is unauthenticated.

Safety

Can touch your log database

Logging does not key a transmitter, so the protection here is about the log. Reads (status, query, fields, search) are marked read-only. Writes, meaning logging, band and mode, notifications, adding, editing or deleting individual records, and the n3fjp_call escape hatch, all sit at the Needs Approval tier, with no extra in-band confirmation. Whole-database operations, raw SQL that could delete or overwrite the entire log, are refused unless N3FJP_ALLOW_DB_WIPE is on; that switch is separate from, and stricter than, the client's approval prompts. Back up your log before ever enabling it. Wherever possible the server leans on N3FJP's own validation and surfaces its responses rather than re-implementing them.
