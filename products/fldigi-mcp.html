fldigi-mcp

An MCP server for controlling fldigi, the amateur radio digital-modem application, from MCP-aware clients such as Claude Desktop. fldigi ships a built-in XML-RPC control interface; fldigi-mcp connects to it and exposes the whole API as a small set of logically grouped tools, so an assistant can read the radio's state and drive the modem, rig, log and transmitter through plain language.

What it does

fldigi's XML-RPC interface is its official, OS-independent control API. fldigi-mcp talks to it directly rather than through an unmaintained wrapper. Every one of the 174 XML-RPC methods in fldigi 4.2.13 is reachable through a named operation in one of 17 grouped tools, one permission each. A coverage test fails the build if a method of the shipped catalog is not wired or an argument type disagrees with fldigi's signature. The Tools table below lists every tool the server offers, including those for diagnostics, band guidance, signal hunting and the proposed patches.

Beyond the API itself, the server adds signal hunting on the receiver audio, an advisory band-guidance feature, and two bundled operating skills distilled from live on-air use. On a fldigi built with two proposed patches, it also reads fldigi's Signal Browser and the RSID bursts its detector heard.

Proposed, not yet in fldigi

The Signal Browser and RSID patches were offered to the fldigi maintainer on 11 and 16 September 2026 (w1hkj/fldigi issue 55). They are not merged and are in no released fldigi. Details are under Features and benefits.

The project is in beta. It supports fldigi 4.2.13, verified live on 9 September 2026. It is an independent project, not affiliated with the fldigi / W1HKJ project.

The license is GPL-3.0-or-later, the same as fldigi, so code can flow both ways. It was MIT through 0.2.2; talking to fldigi over XML-RPC never required the change, porting its decoders does.

Proposed, not yet in fldigi

Two patches were offered to the fldigi maintainer on w1hkj/fldigi issue 55; neither is merged. The Signal Browser patch (11 September 2026) touches four files and adds browser.get_channels and browser.clear. The RSID patch (16 September 2026) applies on top of it and adds rsid.get_hits and rsid.clear, which return each accepted burst as {utc, mode, hz}. Until they are merged, names and fields may change. The server detects the methods in fldigi.list, never from a version number, and caches the result for 30 seconds. On an unpatched fldigi the browser and rsid tools answer with a hint.

To try the Signal Browser patch now, build fldigi from source with it. The RSID patch, patches/fldigi-4.2.13-rsid-hits.patch, applies on top of the first in the same way.

tar xf fldigi-4.2.13.tar.gz && cd fldigi-4.2.13
patch -p1 < /path/to/fldigi-mcp/patches/fldigi-4.2.13-browser-xmlrpc.patch
./configure --prefix=$HOME/.local/fldigi && make -j8 && make install

How it works

fldigi's XML-RPC interface is its official, OS-independent control API, on by default at 127.0.0.1:7362. The server talks to it directly and groups the 174 methods into tools by fldigi area, so "change the mode" is a single permission regardless of which underlying method runs.

fldigi need not run on the same machine. Point the server at it with FLDIGI_HOST and FLDIGI_PORT, and launch fldigi with --xmlrpc-server-address 0.0.0.0. The XML-RPC interface is unauthenticated, so keep the link on a trusted LAN or tunnel it over SSH. Sandboxed clients such as Claude Desktop reach only loopback; mcp-host-bridge does the LAN hop.

Ask it

What is fldigi doing right now? the status tool: version, mode, frequency, T/R, callsign, band Set the rig to 14.070 USB and BPSK31. rig and modem tools; with band guidance on, an advisory note if the frequency is off the segment Find me someone calling CQ on 20 meters PSK31. signal_hunt ranks the steady CQ callers, tune_to picks one, twenty seconds of text confirms it Call CQ Field Day until someone answers. Work them, our exchange is 2A STX, log the contact to N3FJP, then keep calling. with n3fjp-mcp, the full loop: CQ, listen, exchange, TU, log, repeat; transmit is callsign gated stop abort is always allowed; it drops PTT at once and discards queued text
The CQ request keys the transmitter

It works only with a callsign set, and Claude Desktop asks you to approve each time before it keys the radio. Run it first into a dummy load. You are the licensed operator and remain responsible for everything you transmit.

In the packaged desktop extension these appear as a settings form; most users only ever fill in the callsign.

Signal-hunt settings

Two more settings serve signal_hunt. FLDIGI_AUDIO_DEVICE ("Audio input device") names the device fldigi listens to; part of its name is enough, for example iMic. FLDIGI_HUNT_URL ("Signal-hunt tap URL") points at fldigi-mcp-tap where the server cannot reach the sound card, for example http://127.0.0.1:7365.

Safety

Can key a transmitter

The callsign is the single transmit gate. Keying operations (transmit tx, tune, run_macro and send, the wefax and navtex send operations, and any keying method via fldigi_call) refuse unless FLDIGI_CALLSIGN is set. With it blank, the station is receive-only. rx, abort and disable_tx are always allowed because they take the station off the air. Any non-blank value is accepted: club, event, vanity, portable and international calls all work. You remain the control operator under Part 97.

A second layer sits in the client. The server marks read and status tools read-only and the keying tools destructive, so Claude Desktop asks for approval before each on-air action. You can tighten this to Ask or Block on the Tool permissions page. Nothing set there can loosen the callsign gate, which the server enforces.
