serial-console-mcp

AI for the configuration of telecommunication equipment, through the console port it already has. serial-console-mcp connects an assistant such as Claude to the serial console of the equipment that runs networks and radio stations, and of anything else with a serial port. You do not need to know any programming; after it is installed you talk to Claude normally.

What it does

It is not tied to radio. Routers and switches: Juniper (Junos) and Cisco (IOS, IOS-XE) console and craft ports, to log in, read state, change configuration with a safety net (commit confirmed on Junos, reload in on IOS) and leave the console as it was found. Radio transceivers: Icom and Xiegu over CI-V; Kenwood, Yaesu and Elecraft over their text CAT protocols, to identify the rig and read and set frequency and mode. Antenna rotators: Yaesu GS-232 and the many controllers that speak it, to read the heading, turn and stop. And anything else with a serial port: IoT gateways, alarm and access-control panels, UPS and PDU menus, lab instruments, industrial controllers, Linux and BIOS consoles, microcontrollers.

You say what you want in plain language. The assistant drives the console through this server, Claude Desktop asks you to approve each step, and bundled operating skills teach it the Junos and IOS basics: which mode a prompt means, how to get in and out, which show commands answer everyday questions.

Verified on this bench

Juniper support is verified on a real EX2200 console. Cisco, CI-V, CAT and rotator support follows the vendors' protocol references and has not yet met hardware on this bench. The other device types use the generic tools rather than device-specific helpers.

How it works

A serial console is not a simple question-and-answer channel. It echoes what you type, prints unsolicited messages on its own, and can dump pages of output. So the moment a port is open, a background reader keeps draining it into a buffer: the assistant sends a command, then reads until a prompt appears (# , > , login:) to capture the whole reply, or reads whatever is waiting for streaming output.

Ports are opened by name ("rig", "rotator"); tools default to the most recently used one. Several ports can be open at once. The receive buffer is capped at 4 MB per port; if a device streams for hours unread, the oldest bytes are dropped and status says how many.

Ask it

What serial ports do you see? list_serial_ports, with descriptions and USB hardware ids Connect to COM4 at 9600 baud. connect; defaults 9600 8N1, or load a preset Log in as admin and run show interfaces terse, then show me all of it. one expect call: return, login, password, command, read until prompt What is the TS-590 tuned to? query_text("FA;"), then cat_parse Turn the rotator to 45 degrees and confirm. rotator_build, query_text, rotator_parse

Settings

VariableEffect
SERIAL_CONSOLE_READ_ONLY=1Refuse writes except read-style commands (show, ID;, CI-V reads) and refuse control-line changes
SERIAL_CONSOLE_ALLOW=<regex>Override the read-only allowlist
SERIAL_CONSOLE_IDLE_MINUTES=15Auto-close a port idle that long (default: never)

Set them in the server's entry in claude_desktop_config.json under env.

Safety

A console can reconfigure, reboot, or transmit

These tools send exactly what you, through Claude, ask them to send, to whatever device is on the cable. Claude Desktop asks you to approve each tool call, so you see every command before it runs. Read it. This server does not try to guess which commands are dangerous. If something looks wrong, decline it, and keep a real terminal handy for anything you would not want an assistant to type. For a cautious first run on a production console, set SERIAL_CONSOLE_READ_ONLY=1: the server then refuses anything but read-style commands and refuses control-line changes, so it cannot key PTT from RTS or DTR.
